Demo 的伺服器是假的，這些地方不能照搬

Demo 沒有後台：輪次、賽果、賠率、錢包全部在瀏覽器裡模擬。當時的取捨是「能動就好、重點在畫面」，所以它安全只因為沒有真錢。下面列出正式版必須改掉的做法，和可以直接沿用的部分。

只能記三件事的話

  1. 賽果目前可由公開演算法提前算出。正式版要由伺服器以秘密亂數在封盤時抽定，封盤後才下發。
  2. 錢包與結算在 localStorage 和前端程式裡。正式版伺服器是唯一帳本，每筆注單鎖定成交賠率。
  3. 賠率改用 2⁸ 枚舉的解析解，不要沿用蒙地卡羅。B03 曾因次數不夠開出期望值 108.9% 的盤口。

必改：Demo 是假的才沒事 6 項

這些做法在 Demo 是刻意的捷徑，正式版照做會直接造成金錢損失或被破解。

B01

賽果可以被任何人提前算出來

必改
Demo 現況
局號由客戶端時鐘推導：round_no = floor((now − EPOCH) / 40000) + 1，EPOCH = 2026-01-01 UTC。賽果亂數種子由局號派生（mulberry32(round_no × 2654435761 ^ hash("outcome"))），演算法就在前端 JS 裡。所以打開原始碼就能算出未來任一局的賽果。Demo 用這招讓「兩台電腦看到同一場比賽」，沒有伺服器也像全服同步。
正式版
賽果由伺服器用密碼學等級亂數（CSPRNG）、秘密種子產生，在封盤當下抽定。客戶端在封盤前拿不到任何能推出結果的資料，outcome 封盤後才下發。若產品要對玩家證明公平，可加 hash 承諾（開局先公布雜湊、結束後公開種子），屬選配。
出處
js/round-engine.js、js/adapter-b.js 的 rngFor()；管理對話 2026-09-02 已註明「局號種子是公開演算法，Demo 無所謂，正式版由伺服器抽」
B02

錢包、注單、結算全部在瀏覽器裡

必改
Demo 現況
餘額與注單存在 localStorage（gbr_b05r2_save），派彩由前端 adapter-b.js settle() 計算後直接加回錢包。mock-server 雖有 placeBets、冪等鍵與錢包，但轉接層刻意不呼叫，帳本只有引擎那一份。改 localStorage 就能改餘額。
正式版
伺服器是唯一帳本。下注扣款與結算入帳都在伺服器交易內完成，客戶端只顯示伺服器回傳的餘額。前端的 settle() 只能當「顯示用預估」，不能當入帳依據。
出處
js/adapter-b.js 檔頭第 3 條裁決
B03

賠率在客戶端用蒙地卡羅算，而且有噪音

必改
Demo 現況
每局在瀏覽器跑 100 萬次模擬反推四種注別賠率（約 0.65 秒，放在 Web Worker），另外再跑一次「心情全拔」的基準供卡面 ▲▼ 比對，所以是兩次。蒙地卡羅有隨機誤差：B03 曾把規格的「≥100 萬次」誤讀成 10 萬次，B04 掃描發現 0.77% 的盤口期望值超過 100%，最高 108.9%。屬性、心情、賽段全部公開，懂的玩家可以自己精算、只挑開高的盤口下注。改回 100 萬次後，重掃 11,250 個盤口只剩 1 個名目超過 100% 且和雜訊無法區分。
正式版
賠率由伺服器算好隨開局封包下發。建議改用解析解取代蒙地卡羅：出包集合只有 2⁸ = 256 種，四種主注別的機率都能精確枚舉——冠軍與熱門排序 roads.js winProbs() 已經實作；出包＝該隻出包率；零出包＝各隻不出包率連乘；前二連在每個出包集合下按「無放回加權抽樣」的兩步機率加總（只剩一隻完賽時，第二名是出包者中 out_at 最大者，均分；全滅時 28 組均分）。零噪音、毫秒級、各伺服器結果一致，也就不需要 100 萬次的算力。換成解析解後要重跑一次 B04 等級的 RTP 與防套利驗證。
出處
js/tables-b.js 的 MC_RUNS 註解；reports/B04-數值驗證報告.html；js/roads.js 第 39–56 行
B04

大小、奇偶、熱門度三種特殊注別不在接口契約裡

必改
Demo 現況
規格 §10.4 的 round／outcome 契約只有冠軍、前二連、出包、零出包。B10 加的特殊注別由前端 adapter-b.js specialInfo() 自己定價（解析勝率分組加總，賠率 = 0.95 ÷ 機率，向下取兩位），結算也是前端判「冠軍編號屬哪組」。這三種注別的 RTP 沒做過百萬局複驗（規格 §12 Q12）。
正式版
補進契約：開局封包下發七個特殊盤口的賠率，以及熱門度的分組名單（熱門＝勝率前三、冷門＝中間三隻、爆冷門＝末二）。分組必須開局定死、跟著注單存檔，結算時用存下來的名單判定，不能結算時重算——浮點誤差可能讓勝率相近的兩隻換邊。上線前補 Q12：百萬局複驗＋爆冷門（約 5–12x）曝險精算。
出處
js/adapter-b.js 第 262–316 行；規格 §6.1、§12 Q12
B05

注單的賠率要在成交那一刻鎖定

必改
Demo 現況
前端結算時回頭讀當局封包的賠率，沒有每筆注單自己的成交賠率。因為一局之內賠率不變，Demo 沒出錯。
正式版
每筆注單存成交賠率，結算只用它。之後只要做曝險調價、盤口暫停或任何局中變動，沒有這一欄就會算錯錢。mock-server placeBets 的回傳形狀（accepted[].odds）是對的，照它做。
出處
js/adapter-b.js settle()；js/mock-server-b.js placeBets
B06

封盤時間以客戶端時鐘為準

必改
Demo 現況
收注截止由瀏覽器自己的 Date.now() 判定，B09 驗的「歸零後 80ms 拒單」是前端自己拒。玩家手機時鐘不準，局號就會算錯；改時鐘也能騙過前端。
正式版
伺服器時間為準。封盤判定在伺服器；開局封包帶各階段的伺服器時間戳，客戶端只做時差校正，並提早約 300ms 鎖住下注鈕以吸收網路延遲。階段長度只在伺服器定義一次。
出處
js/round-engine.js 第 58–65 行

留意：照著做可以少踩坑 9 項

B07

下注 API 必須冪等，自動下注要防重複

留意
Demo 現況
mock-server 有 idempotency_key（同 key 重送回原結果、不重扣），但轉接層沒用。自動下注的「同局重整不重複下單」靠 localStorage 記住上一次放單的局號。
正式版
客戶端每次送單產生 key，伺服器去重。自動下注規格寫「正式版歸後台排程」，若放伺服器端，停利／停損以結算入帳時點判定，啟動當局算第 1 局（Demo 既定行為）。
出處
js/autobet.js 檔頭；規格 §6.1 自動下注段
B08

曝險上限和盤口額度完全沒做

留意
Demo 現況
規格 §6.5 只留了接口：available: false 加文案「本輪額度已滿」。現行單注上限 5,000、賠率封頂 500x，所以單注最大派彩是 250 萬；前二連冷門組合確實會開到數百倍。
正式版
每局每盤口設累計曝險上限，觸頂轉 available: false。文案沿用「本輪額度已滿」，不寫「禁止下注」。
出處
js/tables-b.js ODDS_CAP、BET_LIMITS；規格 §6.5
B09

路子歷史與近 20 局統計是客戶端重算出來的

留意
Demo 現況
開機時前端用種子把當靴（最多 200 局）全部重放一次來畫路子；歷史局的賠率只用 2,000 次低量模擬重估，所以歷史賠率有幾 % 的誤差。近 20 局「勝 x・包 y」也是重放出來的。
正式版
伺服器提供歷史 API：每局賽果、當時賠率、熱門分組、出包集合。落庫後誤差自然消失。換靴規則（每 200 局清空、介面標「第 N 靴」）由伺服器定義，前端只顯示。
出處
js/adapter-b.js 檔頭回補效能段；B09 報告遺留清單
B10

全滅局照規則結算，不退款

留意
Demo 現況
8 隻全出包時：名次＝出包位置 out_at 倒序（撐最久的是冠軍），冠軍同時算出包；出包注全中、零出包注全輸。機率約 5.6×10⁻⁷／局，Demo 已在聯合分佈內實作。
正式版
後端結算照做並寫單元測試。這種局一年可能遇不到幾次，沒有測試就等於沒驗過。
出處
規格 §5.3；js/mock-server-b.js drawVector()
B11

「前二連」是不計順序，程式裡卻叫 exacta

留意
Demo 現況
前二連押的是前兩名的組合、不計順序（28 組，鍵值小編號在前如 "1-2"）。業界這叫 quinella；exacta 通常指計順序。程式與契約欄位卻用 exacta／odds_exacta。
正式版
正式接口改名（例如 quinella）或在文件明寫「不計順序」，免得有人照字面做成計順序，賠率會差一倍。
出處
js/tables-b.js exactaKey()；規格 §6.1

tables-b.js 仍是「獵豹／袋鼠／烏龜」，畫面顯示「小馬／阿猴／樹懶」（B05-R2 為了配 Kenney 素材只改顯示層）。
正式版
一律以編號 id 1–8 為準，名稱表只存一份。

B13

取整方向與 RTP 驗收判準

留意
Demo 現況
賠率向下取到小數兩位、派彩 floor(注額 × 賠率)，兩次都向莊家。RTP 檔位冠軍／前二連 95%、出包／零出包 94%、特殊 95%，都是 Demo 佔位值。驗收判準實際用 |偏差| ≤ max(0.1pp, 3σ)；規格 §11 寫的「±0.1%」對高賠盤口在可行局數內統計上做不到。
正式版
RTP 正式檔位由營運決定。對帳時把取整收益算進 RTP 分母口徑，和營運先講清楚。
出處
js/tables-b.js RTP；reports/B04-數值驗證報告.html
B14

冷門保護（Q10）沒做，規格文字卻像已實作

留意
Demo 現況
規格 §6.3 描述「連續 N 輪同一隻奪冠就微調下輪權重」，但 §12 Q10 裁決是 Demo 不做。B04 提案：連冠 3 次、下輪權重 ×0.85、賠率隨調整後權重重算（EV 中性）。
正式版
如果要做，只能用全服輪次資料，不可讀任何玩家個人資料（企畫書 §7 合規要求），調整量要計入 RTP。
出處
規格 §6.3、§12 Q10
B15

他人下注流與中獎跑馬燈是捏造的

留意
Demo 現況
ambience.js 用自己的亂數產生暱稱（中段打碼）、金額、目標（按勝率跟熱門），跑馬燈的「大額中獎」也是擬真捏造。
正式版
後端要提供真實的全服下注流與中獎事件（暱稱遮罩規則在後端做）。捏造的中獎播報不能上線。
出處
js/ambience.js

B16

可以直接沿用的部分

參考
Demo 現況
  • 賽果生成三步驟（先擲出包集合與 out_at → 未出包者按權重無放回抽名次 → 出包者按 out_at 倒序沉底）：mock-server-b.js drawVector()，換掉亂數源即可移植。
  • round／outcome 契約形狀（規格 §10.4），以及 placeBets 的錯誤碼：ROUND_LOCKED、MARKET_UNAVAILABLE、INSUFFICIENT_BALANCE、BET_OUT_OF_RANGE。
  • 結算與演出分離：封盤時一次抽定完整賽果向量，演出開始前整包下發，不逐段請求。
  • roads.js 全部是零 DOM 純函式：路子演算法、精確勝率、熱門排序。
  • sim.html 與 B04 的驗證方法：4,000 萬局、45 個盤口逐一掃描期望值。
正式版
新增或修改任何注別，都要整套重驗防套利（窮舉組合、確認沒有期望值超過 100% 的策略）。規格 §6.2 說這是本遊戲最容易出事的地方，B03 的 10 萬次事件就是實例。
